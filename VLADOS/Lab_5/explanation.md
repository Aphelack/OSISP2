# Лабораторная 5 — manager_app (менеджер/воркер)

## Идея лабораторной

Проект демонстрирует многопоточную архитектуру «менеджер — воркер». Главный модуль (`main.c`) создаёт и координирует потоки-работники (`worker.c`/`worker.h`), показывает синхронизацию и обмен данными между потоками.

## Сборка

Сборка через `Makefile`:

```bash
cd Lab_5
make
```

Сборка использует флаги `-pthread` и стандарт C11.

## Запуск

Есть цель `run` в `Makefile`, которая собирает и запускает программу:

```bash
cd Lab_5
make run
# или напрямую
./manager_app
```

Если приложение ожидает аргументы, передайте их при запуске; загляните в `main.c`/`worker.c` для деталей.

## Структура файлов

- `main.c` — точка входа, создание и управление воркерами
- `worker.c`, `worker.h` — реализация потоков-воркеров
- `common.h` — общие структуры/константы
- `Makefile` — сборка и запуск

## Примечания

- Собирается с использованием pthreads; убедитесь, что компилятор поддерживает `-pthread`.
- Код целится на Unix-подобные системы и компилируется `gcc` с `-std=c11`.

## Привязка к коду (объяснение для непрофессионала)

1) Общая идея
	- Проект моделирует простую систему из одного «менеджера» (главный поток) и нескольких «воркеров» (рабочих потоков). Менеджер запускает воркеры, следит за ними и перезапускает упавшие.

2) Основные структуры и параметры — `common.h`
	- `NUM_WORKERS` — число воркеров (в этой версии 4). Это количество потоков, которые менеджер создаёт при старте.
	- `FAILURE_CHANCE` — шанс случайной ошибки у воркера (в процентах). В коде каждая итерация воркера имитирует работу и с некоторой вероятностью завершает свою работу с ошибкой, чтобы показать поведение механизма перезапуска.
	- `worker_info_t` — структура, где хранится идентификатор воркера, дескриптор потока, флаг активности и время последнего «heartbeat» (последней отметки о работе). Это позволяет менеджеру отслеживать состояние каждого воркера.

3) Что делает воркер — `worker.c`
	- Функция `worker_routine` — это то, что выполняет каждый рабочий поток. В цикле воркер «делает задачу» (в коде это имитация задержкой `usleep`) и периодически обновляет поле `last_heartbeat`, чтобы показать, что он жив.
	- Для демонстрации в коде есть случайный сбой: если `rand() % 100` меньше `FAILURE_CHANCE`, воркер печатает сообщение о критической ошибке, помечает себя как неактивный и завершает поток (`pthread_exit`). Это позволяет менеджеру обнаружить падение.
	- Для вывода в консоль используется общий мьютекс `log_mutex`, чтобы сообщения от разных потоков не смешивались.

4) Что делает менеджер — `main.c`
	- Менеджер инициализирует массив `workers`, для каждого воркера создаёт поток с `pthread_create` и сохраняет его дескриптор.
	- В основном цикле менеджер раз в секунду проверяет состояние воркеров. Для проверки он использует `pthread_tryjoin_np` (это ненормативная GNU-функция, которая пытается выполнить `join` без блокировки) — если поток уже завершён, менеджер заметит это и перезапустит воркер.
	- После фиксированного числа итераций (`iterations < 10` в коде) менеджер устанавливает флаг `keep_running = false`, ждёт завершения всех потоков через `pthread_join`, уничтожает мьютекс и корректно завершает работу.

5) Синхронизация и корректное завершение
	- `log_mutex` гарантирует, что вывод в консоль происходил атомарно (полное сообщение одного потока выводится без вмешательства другого). Это упрощает чтение логов во время одновременной работы нескольких потоков.
	- Флаг `keep_running` — глобальная переменная, отмеченная как `volatile`, используется воркерами, чтобы узнать, когда им следует завершиться корректно.

6) Запуск и тестирование
	- Собрать и запустить:

```bash
cd Lab_5
make
make run
```

	- При запуске вы увидите сообщения от менеджера и воркеров. Менеджер будет перезапускать упавшие потоки и в конце аккуратно завершит систему.

## Советы и возможные улучшения

- В реальных приложениях вместо `rand()` для имитации отказов используют реальные ошибки (например, ошибки сети, I/O и т.д.).
- Проверка завершения потоков через `pthread_tryjoin_np` — небезопасна для переносимости (GNU-специфично). В более переносимых решениях используют дополнительные флаги или условные переменные для уведомления менеджера о состоянии воркера.
- Можно расширить обмен данными между менеджером и воркерами, например, добавить очередь задач, где менеджер кладёт задания, а воркеры берут их на выполнение.
